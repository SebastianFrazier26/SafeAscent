# SafeAscent: agent guide

Climbing-route risk forecasts from historical accident data and weather. FastAPI + Celery backend on Railway, PostGIS on Neon, React frontend. Read `README.md` for the point of the project and `DATA_LICENSE.md` before touching data.

## Commands

Backend (run from `backend/`):
- `uv sync`: install (lockfile committed; CI runs `uv sync --frozen`). `default-groups = ["dev", "pipelines"]` in `pyproject.toml`, so a plain `uv sync` already installs the `pipelines` group (`timezonefinder`, `tzdata`) the local-day/ERA5 jobs and their tests need. `uv sync`'s groups are exact — `uv sync --group dev` alone drops `pipelines` rather than adding to the default set, so name both groups if you narrow the sync. The API image builds with `--no-group pipelines` (not needed at serve time).
- `uv run pytest`: tests. `needs_data` tests (populated DB/live services) are deselected by default (`-m 'not needs_data'`); run them explicitly with `-m needs_data`. Tests that need a throwaway Postgres (`tests/test_migrations.py`, `test_roles_phase2.py`, `test_migration_0004.py`, `test_ingest_log.py`, `test_mp_ticks_quarantine.py`, `test_mp_tick_aggregates.py`, and others built on `tests/pgtest.py`) need `MIGRATIONS_TEST_ADMIN_URL` (a superuser URL to a maintenance DB) and skip without it; the role-script tests (`test_migrations.py`, `test_roles_phase2.py`) also need `psql` 15+ on `PATH` (under `CI=1` a missing `psql` fails instead of skipping). `VERIFY_DATABASE_URL=<analyst url> uv run pytest -m db tests/verify`: read-only acceptance checks against a live branch or prod; `db`-marked tests are excluded from the default `uv run pytest` (`addopts` deselects `not needs_data and not db`) and skip individually without `VERIFY_DATABASE_URL`.
- `uv run ruff check . ../scripts/`: lint (rules `E4,E7,E9,F`, pinned ruff 0.8.4). Covers all of `backend/` (ruff's default excludes skip `.venv`, `__pycache__`, etc.) plus the top-level `scripts/`.
- `uv run mypy`: types. Scope comes from `pyproject.toml` (`files = ["app"]`); most of `app/` is an ignore-errors allowlist until typed, strict on `app.config`, `app.services.risk_bands`, `app.healthchecks`, and all of `app.pipelines` (`app.pipelines`, `.validate`, `.grid`, `.ingest_log`, `.db`, `.mp_ticks_quarantine`, `.mp_tick_aggregates`, `.textsim`, `.geo`, `.gnis`, `.open_meteo`, `.cell_conditions`, `.localday`, `.pro_window`, `.era5_fill`, `.normals`, `.era5_window`, `.r6_verify`), `app.data.repair.*` (`framework`, `sources`, `review`, `dates`, `checks`, `severity`, `geocode`, `activity`, `dedupe`, `experience`, `area_weekly`, `__main__`), and, minus the subclassing-Any check SQLAlchemy's `declarative_base()` always trips, `app.models.pipeline`, `app.models.reference` and `app.models.conditions`, with a celery-adjacent variant (same flags minus the subclassing-Any/untyped-decorator checks celery's own missing types always trip) on `app.celery_signals` and `app.tasks.ops` — extend either list as modules graduate.
- `uv run python -m app.pipelines.<job>`: Phase 2 data jobs (`mp_ticks_quarantine`, `mp_tick_aggregates`, `gnis --file <DomesticNames zip>`, `localday register`, `era5_window register|plan|run --window-start YYYY-MM-DD [--initial-window] --max-units N` — the only ERA5 entry point; refuses outside a Professional window — `r6_verify`); connect as `ingest` via `INGEST_DATABASE_URL` and refuse without it.
- `uv run python -m app.data.repair <step> [--apply]`: Phase 2a accident repairs as `ingest` (dry run by default; `--apply` writes, audited per field in `internal.accident_revisions`). Rule steps: `r2r1`, `r9`, `r3` (R3a/R3 geocodes; needs GNIS loaded), `r4` (activity classes; needs `r3`), `r5` (duplicates; needs `r3` and `r4`; `--apply --out` also writes the owner review CSV), `r12` (experience facts), `r7` (one-time `area_weekly_weather.longitude` sign fix; refuses unless exactly one row is positive and equals 113.2). Read-only checks: `r3-states` (raw state values: unmapped and foreign ones need the owner before `r3 --apply`), `r3-clusters`. Owner round trips, each `*-export --out` once (refuses to replace a file unless `--overwrite`) then `*-import --review-file` (`--apply` where it writes rows): `r1`, `r9`, `r3a`, `r3-plot`, `r3-ambiguous`, `r4-review`, `r5-import`; golden draws `r4-golden-export`, `r12-golden-export`. Runbooks call it through `backend/scripts/runbook_helpers.sh`, which refuses unless `TARGET_HOST` is set (a Neon branch host, or `production`). It also holds the prod-gate helpers (`same_ids`, `gate_pass`/`gate_require`) and `bg_start`/`bg_wait` for applies longer than an agent's 10-minute tool call; a runbook block never defines a helper for a later block.
- `uv run alembic upgrade head`: migrations. Needs `MIGRATOR_DATABASE_URL` (the `migrator` role). Never runs on app startup; prod is `alembic stamp 0001_baseline` once, then upgrades from there.
- `uv run uvicorn app.main:app --reload`: API
- `uv run celery -A app.celery_app worker --loglevel=info --concurrency=2 -E` and `uv run celery -A app.celery_app beat --loglevel=info --schedule=/tmp/celerybeat-schedule`: background jobs (beat is a separate process/service from the worker, never combined)

Frontend (run from `frontend/`): `npm ci`, `npm run dev`, `npm test` (watch), `npm run test:run`, `npm run lint`, `npm run typecheck`, `npm run build` (CI also sets `VITE_API_BASE_URL`/`VITE_MAPBOX_TOKEN` build args). `frontend/docker-tests/test_images.sh all` builds and HTTP-checks both `MAINTENANCE_MODE` image variants.

Local stack: `docker compose up --build` (db, redis, api, worker, beat, frontend — same images and start commands as Railway). `scripts/check_compose_matches_railway.py` (CI `guards` job) fails if they drift.

## Service topology

- Railway services: `api` (`backend/railway.toml`), `worker` (`backend/railway-worker.toml`), `beat` (`backend/railway-beat.toml`, exactly one replica — a second double-schedules every task), and `frontend`. One Redis. Postgres/PostGIS on Neon.
- Deploys: Railway auto-deploys `main` after the `ci-ok` check is green ("Wait for CI"); auto-deploy is off until the Phase 1 relaunch. Migrate before deploy: code whose models map columns a pending migration adds (e.g. `0004`) must not deploy until that migration is on prod (`DEPLOYMENT.md`).
- Alerting: healthchecks.io dead-man checks for the nightly job (`HEALTHCHECKS_NIGHTLY_URL`) and the beat heartbeat (`HEALTHCHECKS_BEAT_URL`). An unset ping URL skips the outbound call with a WARNING (local/CI never call out). `GET /health/worker` returns 503 when the worker heartbeat (`WORKER_HEARTBEAT_TTL_SECONDS`, default 120s) is missing from Redis, and reports the trailing 7-day expired-task counts.

## Database and migrations

- Alembic lives in `backend/alembic/`. `0001_baseline` replays a committed, sanitized schema-only dump (`0001_baseline.sql`); prod is stamped at it, never upgraded through it. `0002_drop_ascents_climbers` and `0003_hist_insufficient_data` (nullable historical `risk_score`) follow, then `0004_phase2a_foundation` (schema `internal`, the `accidents_raw` snapshot, repair columns, run log), `0005_gnis_duplicate_decisions` (`gnis_summits`, `internal.duplicate_decisions`), `0006_accidents_clean` (views `accidents_clean`/`accidents_clean_daily`, what Phase 3 reads) and `0007_cell_daily_conditions` (`cell_daily_conditions`, `grid_bucket_series`, the normals tables, `accidents.tz`, the `accident_conditions` view). 0002 raises on downgrade; 0003 refuses to downgrade while any `historical_predictions` row has a NULL `risk_score`; 0004/0005 refuse while their tables or columns hold data; 0006 refuses while anything depends on its views; 0007 refuses while `cell_daily_conditions`, `cell_climate_normals` or `cell_climatology` holds any row (paid ERA5 data). Revision ids fit `alembic_version`'s VARCHAR(32). Treat every revision as forward-only unless you know otherwise.
- Every schema change is a new revision, rehearsed on a Neon branch first, then run as an explicit step with `MIGRATOR_DATABASE_URL` — never at app startup, never autogenerated blind.
- No DDL in `app/`; `tests/test_no_runtime_ddl.py` greps for `CREATE`/`ALTER TABLE`/`DROP` and fails the build if any appears.
- Roles are created **only via SQL as the owner** (`backend/db/roles/create_roles.sql`, `verify_roles.sql`), never via neonctl, the Neon Console, or the Neon API — those grant `neon_superuser`. Current roles: `migrator` (DDL, owns schema objects), `app` (SELECT on all tables; writes only `historical_predictions` and its id sequence), and `analyst` (pre-existing, read-only: SELECT via default privileges; must exist before `create_roles.sql` runs); `ingest` (Phase 2 data jobs: reads and writes only the objects listed in `backend/db/roles/verify_roles_phase2.sql`, including column-level grants that keep `mp_ticks.climber_name` out of every grant and every narrative column out of its `UPDATE` grant on `accidents` and out of its `SELECT` grant on `internal.accidents_raw` (it has table-level `SELECT` on `accidents`: R4, R5 and R12 read narratives in memory, never into output); its URL must verify TLS — `app.pipelines.db` refuses anything weaker than verify-full on a remote host) and `trainer` (NOLOGIN, no grants until Phase 3, which grants it the `accidents_clean` views, never `accidents`) are created by `create_roles_phase2.sql`, which also creates schema `internal` (owned by `migrator`; `app` has no access). After every Phase 2 migration the owner runs `grants_phase2.sql` (idempotent; as `migrator`, or as an owner holding `SET` on `migrator`) then `verify_roles_phase2.sql`. `triage_worker` lands in Phase 4. Passwords are generated into the role's env file (`backend/scripts/write_role_url.py --role <r> --env-file .env.<r> --generate-password`) and reach `backend/db/roles/create_roles.sql` (`MIGRATOR_PASSWORD`/`APP_PASSWORD`) and `create_roles_phase2.sql` (`INGEST_PASSWORD`, from `.env.ingest`) as plaintext via `\getenv`, never argv, over verify-full TLS; the server stores SCRAM-SHA-256. Neon rejects pre-hashed SCRAM verifiers, so both scripts refuse verifier-shaped or sub-32-character values, and refuse to rerun once their roles exist. The prod Neon branch is `production`. Role credentials live in gitignored `backend/.env.<role>` files — **agents never read or print those files.**
- The legacy `routes`/`mountains` tables and the FKs from `accidents` stay until Phase 2a; don't touch them in Phase 1 work.

## Data rules

- **No scraper code is ever committed to this repo.** CI's `guards` job runs `scripts/check_no_scrapers.py` on every tracked file (names, banned-host mentions, HTML-parsing/browser-automation imports, and lockfile entries). Clients for open APIs (OpenBeta GraphQL, Open-Meteo, NOAA, USGS, Macrostrat, NWS, AirNow, SNOTEL) are fine and live in the repo.
- Mountain Project: ice/mixed route facts (name, grade, location, type), rock routes, and tick aggregates (ascent counts by season/month) may be displayed; none is bulk-redistributed. No MP prose or descriptions, ever, anywhere — not fixtures, docs, or commits. (Owner decision 2026-09-28; `DATA_LICENSE.md` wording is pending the owner's legal review.)
- OpenBeta climb/area data is CC0; see `DATA_LICENSE.md` for the full source-by-source breakdown and verification dates.
- Weather days are the crag's local calendar day: conditions are keyed by `(grid_bucket, tz, date)`; join accidents through `accidents.tz`. `record_kind = 'stopgap'` rows are Forecast-API past days, not ERA5. Precedence is `era5 > stopgap > forecast` (the upsert's WHERE); a re-fetch that comes back NULL never erases a stored value at equal rank, but an `era5` row still replaces a lower-kind row whole.
- Incident ERA5 history starts `localday.INCIDENT_START` (1990-01-01, owner decision DP1); each incident series' fill reaches back to 1989-12-26 (6 days before, for the first 7-day window). An incident dated before 1990 gets no incident series at all and reads `conditions_missing`, never a zero.
- `era5_window`'s trailing re-fetch of each series' last 90 days (ERA5T → final ERA5 replacement) happens once per Professional window, not once per run inside it.
- A Professional month is capped at 5,000,000 Open-Meteo units (`pro_window.WINDOW_UNITS`); the plan gate refuses to buy anything once cumulative spend would pass 4,500,000 (`PLAN_STOP_UNITS`). A fill run's failure breaker stops the window after 3 consecutive failed or rejected chunks/batches, so an outage cannot run the budget down unattended.
- The live app reads historical weather only from `cell_daily_conditions` in our own database — it never calls Open-Meteo at request time. The legacy `weather` table stays only as read-only input to `r6_verify`'s one-time agreement check; it is otherwise unused (`data/DATABASE_STRUCTURE.md`).

## Safety-accuracy rules (owner priority: accurate results over everything else)

- Never display a fabricated risk score. No `|| 0` / `?? 0` (or equivalent) on a risk value in either stack — a missing, malformed, or failed score renders as "Unavailable"/em-dash in neutral gray, never a number. Backend: `tests/test_no_fabricated_risk.py`. Frontend: `riskUtils.test.ts`.
- One risk-band definition: `backend/app/services/risk_bands.py`'s `RISK_BAND_THRESHOLDS` (25/50/75, lower-inclusive) mirrored by `frontend/src/utils/riskUtils.ts`. `backend/tests/test_risk_bands.py` fails if they drift — change both together.
- Insufficient-data rule: no contributing evidence, or a raw score below `MIN_ESTIMABLE_SCORE` (0.05), renders "Too little evidence to estimate risk yet" in gray (`insufficient_data`/`INSUFFICIENT_DATA_COLOR`) rather than a score. Interim until the Phase 3 model borrows evidence from characteristically similar routes anywhere.

## Conventions

- Python 3.12, uv, ruff, pytest, mypy. Frontend: React 19 + Vite. New frontend modules are TypeScript; convert a `.js`/`.jsx` file when you substantially change it. Tests stay in the language of the component under test (a `.jsx` component keeps a `.jsx` test).
- Comments are load-bearing only: why, not what. No banner or narration comments.
- `CHANGELOG.md`: one dated entry per merged PR, Keep a Changelog format.
- Branch per change off `main`. PR plus green `ci-ok` required (the only required check; jobs are `backend`, `frontend`, `guards`, `ci-ok`). No direct pushes or force-pushes to `main`. Never push on your own initiative — only when the owner invokes `/commitandpush`.
- Secrets never go in the repo. `.env.example` mirrors `app.config.Settings` fields exactly plus the `VITE_*` build args (`Settings` uses `extra="forbid"`); `tests/test_env_example_parity.py` enforces this — add the line there whenever you add a `Settings` field.
