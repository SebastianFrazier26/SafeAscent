### Phase 1 PR6 — 2026-09-27

- New `backend/app/healthchecks.py`: `ping(url, suffix, *, transport=None, timeout=10.0)` sends a dead-man's-switch ping to healthchecks.io (`/start` before a job, bare success ping, `/fail` on error) so the nightly safety job — which previously hung for a month unnoticed — reports its own liveness. It never raises: an unset URL is skipped with a WARNING and makes no outbound call, and any exception — an `httpx.HTTPError` from a network failure or non-2xx status, or `httpx.InvalidURL` from a malformed env value — is caught, logged by exception type only, and returns `False`. The URL is stripped and never logged, since it is the check's credential. New `backend/tests/test_healthchecks.py` covers suffix handling, the unset-URL skip, HTTP error statuses, and that a network error is swallowed without the URL leaking into logs; all cases inject an `httpx.MockTransport` so no real network call is made.
- New `backend/app/celery_signals.py` makes a hung worker consumer and silently expiring tasks visible (the 2026-08 outage: the consumer hung while embedded beat kept publishing, and every nightly message expired unlogged). `HeartbeatStep`, a Consumer bootstep that starts after the task consumer, writes `celery:worker:heartbeat` (epoch seconds, TTL `WORKER_HEARTBEAT_TTL_SECONDS`, default 120s) every TTL/3 on the consumer's timer. With prefork on the Redis broker, the consumer's event loop drives that timer, so the key lapses when the loop stops. The heartbeat is rescheduled exactly once when the consumer restarts after a broker error, which clears the timer. A consume socket that dies silently, or a `-P gevent`/`eventlet` pool, is left to the beat healthchecks ping. A `task_revoked` handler logs every revocation at ERROR and, for expired tasks, increments `celery:expired:<task>:<YYYY-MM-DD>` (UTC, 8-day TTL). `read_worker_health()` returns `status` (`ok`/`down`), the heartbeat age, and per-task expired counts over the last 7 days; it reports `down` when Redis is unavailable or a stored value is garbage. `install(app)` registers both. New dev dependency `fakeredis==2.38.0`; `backend/tests/test_celery_signals.py` covers the reader, the counter window, the signal handler, and the bootstep against fakeredis.
- Celery beat now runs as its own Railway service (`backend/railway-beat.toml`, exactly one replica, `--schedule=/tmp/celerybeat-schedule`). The worker (`backend/railway-worker.toml`) no longer embeds `--beat` and runs with `-E` and `--concurrency=2`, so `beat_heartbeat` has a free slot while the ~2h nightly run holds the other; the nightly Redis population lock (`SET NX`) keeps a second nightly from overlapping. Stale-lock recovery now fails closed: it takes over the lock only when `inspect().active()` answers and shows no other nightly run. If the inspect raises, times out, or gets no reply, the lock is kept, a WARNING is logged, and the 6h lock TTL frees a crashed holder. Embedded beat is how the 2026-08 outage went silent: the consumer hung while beat kept publishing, and every nightly message expired unlogged. The compose `beat` service uses the same command. `backend/run_celery_worker.sh`/`run_celery_beat.sh` removed. Creating the Railway `beat` service is an owner step.
- `app/celery_app.py` now calls `celery_signals.install()` (consumer heartbeat + expired-task accounting), sets `worker_cancel_long_running_tasks_on_connection_loss=True` so a lost broker connection cancels in-flight work for `acks_late` redelivery, and schedules `app.tasks.ops.beat_heartbeat` every 900s (`expires` 600). That task runs on the worker and pings `HEALTHCHECKS_BEAT_URL`, so the beat check proves both scheduling and consumption. healthchecks.io checks: beat = 15 min period + 60 min grace (a dead consumer alerts within 75 min); nightly = 24h period + 4h grace.
- The nightly `compute_daily_safety_scores_optimized` pings `HEALTHCHECKS_NIGHTLY_URL` with `/start`, then success or `/fail` (the error is re-raised). A run skipped by the population lock sends no pings. Computation and return value are unchanged; ping failures never fail the task.
- CI `guards` job: new stdlib `scripts/check_compose_matches_railway.py` fails if the compose `worker`/`beat` command differs (by argv) from the matching Railway `startCommand`. Previously only service names were compared. Tests: `backend/tests/test_celery_ops.py`, `backend/tests/test_check_compose_matches_railway.py`.
- Fix round (2026-09-28): the nightly task now sets `soft_time_limit=5h`/`time_limit=5.5h` (below the 6h lock TTL and broker `visibility_timeout`), so a hung run is killed by Celery before its lock could expire and let a redelivered message start a duplicate on the worker's second slot; `SoftTimeLimitExceeded` is an `Exception` subclass, so it already takes the existing failure path (`/fail` ping, lock released in `finally`, re-raised) with no code change there. Celery's soft time limit is signal-based (`SIGUSR1`) and works with the default prefork pool on Linux, which is what both the worker and CI run. The stale-lock recovery's `inspect().active()` census (`_get_active_optimized_task_ids`) assumes a single worker replica, matching `numReplicas = 1` in `backend/railway-worker.toml`; both files now say so.
- New public `GET /health/worker`: 200 `{"status":"ok","last_heartbeat_age_seconds":...,"expired_tasks_7d":{...}}` when the heartbeat is fresh, else 503 with `status: "down"`. It only ever returns coarse status/age/counts from `read_worker_health()` — never a Redis host, exception text, or task arguments — and is deliberately not the Railway API healthcheck path, so a worker outage doesn't take the API down with it. New `backend/tests/test_worker_health_route.py` covers the fresh-heartbeat, no-heartbeat, and no-Redis cases against fakeredis/`TestClient`.

- Least-privilege DB roles, created only through SQL run as the owner (never neonctl/Console/API, which add `neon_superuser`). `backend/db/roles/create_roles.sql` creates `migrator` and `app` (`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT`) and requires PostgreSQL 16+. It moves ownership of every non-extension table/view/sequence/routine/enum/domain in `public` to `migrator`, the only role with `CREATE` on `public`. The owner keeps `migrator` membership `WITH SET, INHERIT` until the relaunch gate revokes it, so services still on the owner URL keep working.
- `app` is read-mostly: `SELECT` on every table except `alembic_version`, plus `INSERT, UPDATE, DELETE` only on `historical_predictions` and `USAGE` on its id sequence (the nightly upsert and purge in `app/tasks/safety_computation_optimized.py` are the app's only writes; `app/` was re-grepped for others). Default privileges make tables `migrator` creates later `SELECT`-only for `app` and `analyst`; a migration that needs app writes grants them per table.
- Passwords never reach the server: `create_roles.sql` reads SCRAM-SHA-256 verifiers from `MIGRATOR_PASSWORD_SCRAM`/`APP_PASSWORD_SCRAM` via psql `\getenv` and refuses values that are not verifiers, since Postgres would otherwise store a pasted plaintext as the password. The role test confirms the stored `rolpassword` is the verifier, the right password logs in and a wrong one is rejected, and no plaintext appears in the SQL psql sends or in `pg_stat_statements`.
- `backend/db/roles/verify_roles.sql` checks the following and exits non-zero on any miss:
  - no superuser/createdb/createrole/replication/bypassrls;
  - `NOINHERIT` on `migrator`/`app`, and the three roles hold no memberships;
  - only `CURRENT_USER` is a member of `migrator`;
  - nobody can `SET` or inherit `app` (PG16's automatic ADMIN-only grant to the creating owner is allowed);
  - schema/database `CREATE`, ownership, and exact per-table `app` DML (writes only on `historical_predictions`);
  - `analyst` has no `INSERT/UPDATE/DELETE/TRUNCATE`;
  - sequence grants, and that `pg_default_acl` is exactly `SELECT` to `app` and `analyst`.
- New `backend/scripts/write_role_url.py`, with `--role` limited to `migrator`/`app`:
  - `--env-file <path>` builds `<ROLE>_DATABASE_URL` (asyncpg, `ssl=require`, password URL-escaped) from `OWNER_DATABASE_URL`'s host/db and `<ROLE>_PASSWORD`, and writes it via `mkstemp` (0600) plus atomic `os.replace`, so an existing 0644 file never holds the secret at a looser mode.
  - `--scram` prints the role's SCRAM-SHA-256 verifier (`scram_verifier()`, stdlib PBKDF2/HMAC, checked against the RFC 7677 example exchange), reading the password from `<ROLE>_PASSWORD` or `--password-stdin`, never argv.
  - Neither mode prints a password.
